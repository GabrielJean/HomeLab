## Installation Media Presets (`Omni/media/`)

Declarative `InstallationMediaConfigs` define the exact Talos OS images generated by the Talos Image Factory (`factory.talos.dev`) for each Proxmox node.

| File | Preset ID | Platform | Extensions | Auto-Labels | Notes |
| :--- | :--- | :--- | :--- | :--- | :--- |
| [`media/talos-1.yaml`](media/talos-1.yaml) | `talos-1` | `nocloud` (Proxmox) | `siderolabs/qemu-guest-agent` | `pve-1: ""` | NVIDIA LTS extensions commented until GPU passthrough is configured |
| [`media/talos-2.yaml`](media/talos-2.yaml) | `talos-2` | `nocloud` (Proxmox) | `siderolabs/qemu-guest-agent` | `pve-2: ""` | CPU-only node (no GPU) |

### 1. Apply Media Presets to Omni (GitOps)
```bash
omnictl apply -f Omni/media/
```

### 2. Manage and Download via CLI
```bash
# List all registered installation media presets:
omnictl media preset list

# Download ISO directly using the preset:
omnictl media download talos-1 --output /path/to/isos/
omnictl media download talos-2 --output /path/to/isos/
```
*(Alternatively, download directly from the Omni Web Dashboard under **Installation Media**).*

### 3. Modifying Extensions on Existing Running Nodes
To add or remove extensions on a node that is already running without reinstalling:
```bash
# Edit node extensions directly via omnictl:
omnictl edit extensionsconfiguration schematic-<machine-id>
```
Omni will automatically generate a new schematic, stage the update to the alternate A/B partition slot, and perform an in-place reboot.

## 4-Step Bootstrap Walkthrough

### Step 1: Boot the VM in Proxmox

1. **Apply Media Presets to Omni (GitOps)**:
   ```bash
   omnictl apply -f Omni/media/
   ```
   *(Registers declarative presets [`talos-1.yaml`](media/talos-1.yaml) and [`talos-2.yaml`](media/talos-2.yaml) with Talos 1.14.4, NoCloud cloud-init, QEMU guest agent, and auto-matching labels).*

2. **Download Boot Media from Omni**:
   - **Via CLI**:
     ```bash
     omnictl media download talos-1
     omnictl media download talos-2
     ```
   - **Via Web UI**: In your [Omni SaaS Dashboard](https://omni.siderolabs.com), open **Installation Media**, locate `talos-1` or `talos-2`, and click **Download ISO**.
3. Upload the ISO to Proxmox and create your VM (`talos-1` on `pve-1` or `talos-2` on `pve-2`). Ensure **QEMU Guest Agent** is enabled in Proxmox VM options.
4. Boot the VM.

---

### Step 2: Apply Machine Classes and Label Machines in Omni

1. **Apply the Machine Classes to Omni**:
   ```bash
   omnictl apply -f Omni/classes/
   ```
   *(This registers the `pve-1` and `pve-2` machine selectors in Omni).*

2. **Label the Discovered Machine in Omni**:
   Once booted, the node connects over SideroLink and appears in the Omni UI under **Machines**:
   - In the Omni dashboard, click the discovered machine.
   - For Home 1: add label **`pve-1`**
   - For Home 2: add label **`pve-2`**

*(Omni's Machine Classes match this label automatically—no UUIDs needed in Git).*

---

### Step 3: Sync the Cluster Template
From this repository, push the declarative cluster configuration to Omni:

```bash
# For Home 1 (k8s-talos-1):
omnictl cluster template sync -f Omni/clusters/k8s-talos-1.yaml

# For Home 2 (k8s-talos-2):
omnictl cluster template sync -f Omni/clusters/k8s-talos-2.yaml
```

Omni will automatically:
- Allocate the labeled node to the cluster.
- Apply the single-node patch (`allowSchedulingOnControlPlanes: true`).
- Enable native NetworkPolicies on Flannel.
- Apply site-to-site static routes between Home 1 and Home 2 via local Tailscale routers.
- Bootstrap etcd and Kubernetes.

---

### Step 4: Get `kubeconfig` and Verify
Fetch the admin credentials routed through Omni's secure WireGuard proxy:

```bash
# Merge credentials into your ~/.kube/config:
omnictl kubeconfig -c k8s-talos-1 --service-account --user admin --force-context-name admin@k8s-talos-1 --force
omnictl kubeconfig -c k8s-talos-2 --service-account --user admin --force-context-name admin@k8s-talos-2 --force

# Verify the clusters:
kubectl --context admin@k8s-talos-1 get nodes
kubectl --context admin@k8s-talos-2 get nodes
```

## Automated S3 etcd Backups

Omni natively supports continuous `etcd` snapshots stored directly to S3 or S3-compatible object storage (AWS S3, Cloudflare R2, MinIO, Backblaze B2, etc.).


### 1. Schedule Backups in Cluster Templates
Both [`k8s-talos-1.yaml`](clusters/k8s-talos-1.yaml) and [`k8s-talos-2.yaml`](clusters/k8s-talos-2.yaml) have automated backups configured under `features.backupConfiguration`:

```yaml
features:
  backupConfiguration:
    interval: 1h  # Automatically snapshots etcd every hour
```

When you run `omnictl cluster template sync -f ...`, Omni immediately triggers an initial backup and schedules recurring snapshots according to this interval.

### 2. Check Backup Records
```bash
# List all etcd backups for a cluster:
omnictl get etcdbackup --selector omni.sidero.dev/cluster=k8s-talos-1
```

## Automated Omni GitOps (GitHub Actions)

Cluster templates, machine classes, and installation media presets are automatically synchronized to Sidero Omni SaaS via GitHub Actions:

- **Workflow**: [`.github/workflows/omni-gitops.yml`](../../.github/workflows/omni-gitops.yml)
- **Execution Matrix**:
  - `pull_request`: Runs offline validation (`omnictl cluster template validate`) on modified templates.
  - `push` (branches: `main`, `k8s-migration`): Validates templates, applies machine classes and media presets, and syncs cluster templates with verbose output.
  - `workflow_dispatch`: Manual execution from GitHub Actions UI.

### GitHub Repository Secrets
To authenticate the workflow with Omni, configure the following repository secrets in GitHub (**Settings > Secrets and variables > Actions**):
- `OMNI_ENDPOINT`: Omni SaaS API endpoint (found in `~/.talos/omni/github-actions-sa.yaml`).
- `OMNI_SERVICE_ACCOUNT_KEY`: Service account key generated via `omnictl serviceaccount create github-actions`.

## Control Plane Structured Authentication (OIDC)

Starting with Talos Linux v1.14+, legacy command-line arguments under `cluster.apiServer.extraArgs` (such as `--oidc-issuer-url`, `--oidc-client-id`) are prohibited. Instead, Talos manages API server authentication through the native Kubernetes **Structured Authentication Configuration** (`AuthenticationConfiguration`) using modular `KubeAuthenticationConfig` documents.

### Declarative Patch: `patches/oidc-azure-ad.yaml`

Microsoft Entra ID (Azure AD) authentication is declared as a reusable patch in [`clusters/patches/oidc-azure-ad.yaml`](clusters/patches/oidc-azure-ad.yaml):

```yaml
apiVersion: v1alpha1
kind: KubeAuthenticationConfig
configuration:
  apiVersion: apiserver.config.k8s.io/v1beta1
  kind: AuthenticationConfiguration
  jwt:
    - issuer:
        url: https://login.microsoftonline.com/10b7061b-f2d0-4778-8cae-2666faf4af25/v2.0
        audiences:
          - e1d55ddd-3453-4a91-9842-aa7d7dc620a3
      claimMappings:
        username:
          claim: preferred_username
          prefix: ""
```

### Static Pod Lifecycle & Verification:
1. **Replacement Semantics**: In Talos, `KubeAuthenticationConfig.configuration` completely replaces the inner payload rather than performing a deep merge.
2. **Static Pod Re-rendering**: When this patch is added or updated, Talos's `k8s.StaticPodServerController` renders an updated `kube-apiserver` manifest (`old_version` -> `new_version`).
3. **Recreation Delay**: During container recreation (~45–90 seconds), the API server initializes caches and webhooks. Omni temporarily reports `Load Balancer Not Ready` or `proxy error` until health checks pass and SideroLink tunnels re-establish.
4. **Kubelet RBAC**: Ensure `ClusterRoleBinding/apiserver-kubelet-admin` is active so that kubelet webhook authorization does not fail when static pod status controllers query node endpoints.
